# 备忘录：项目上下文管理体系（讨论稿，未实施）

日期：2026-08-16

## 一、起因

1. 记忆区（agent 的持久记忆）涨到 98% 溢出，被迫把 WordBattle 细节（构建命令、测试机制）挪到项目 docs，记忆只留指针。
2. 发现 docs 下堆积 10 个"交接_xxx.md"，纯追加不合并，越堆越难用。
3. 由此讨论出"项目/事项纪律文件化 + 记忆存目录指针 + 按场景加载"的模式，并进一步抽象成通用的上下文管理体系。

## 二、核心模型：按"加载时机"分四层

判断依据是 token 经济学：LLM 每次调用都会重新编码整个上下文，进入上下文的内容在后续每一轮都持续付费。所以分层的标准不是"主题"，而是"什么时候读、读完要陪多久"。

| 层 | 载体 | 加载时机 | 放什么 | 铁律 |
|---|---|---|---|---|
| 1. 常驻层 | agent 记忆 / 技能索引 | 每轮自动 | 铁律（错了代价大的）+ 项目目录（路径 + 文件清单 + 各管什么场景） | 绝不放细节 |
| 2. 索引层 | 项目内总览文件（README 或 00_索引.md） | 进入项目时先读 | 项目当前状态、路由表（什么情况去读哪个文件） | 负责路由，不展开 |
| 3. 纪律/细则层 | 按**操作场景**分的文件（测试、构建发布、编码约定…） | 对应场景发生时才读 | 规矩 + 每条带"起因/为什么" + 文件头一行声明适用场景 + 尾部修改记录 | 场景划分，不按主题细分 |
| 4. 历史层 | 事件记录（踩坑、排查、交接） | 需要追溯时才读 | 过程性材料 | **定期合并归档**，不无限追加 |

## 三、配套流转规则（体系的灵魂）

1. **上升**：某条纪律在多个项目反复需要，或错了代价极大 → 提炼成一句话进记忆/技能。
2. **下沉**：记忆里发现某条只是细节 → 挪进项目文件，记忆只留指针。
3. **压缩**：历史层的事件文件定期合并成"当前状态 + 重要决策"文档，旧文件归档不再读。事件视角（过程）与状态视角（现在）不混在一个不断追加的文件里。

判断信号：记忆占用逼近上限 = 该下沉了；某个纪律文件膨胀到几十条以上 = 该拆分了；同一句纪律出现在两个项目 = 该上升了。

## 四、几个关键细节（讨论中纠正过的认知）

1. **指针必须做成目录**：记忆里不能只写"测试前读测试纪律"，要写成"每个文件一行：文件名 + 一句话 + 什么场景读"。LLM 要能按情形自动加载，前提是先知道有哪些文件。目录本身短（几个文件几行），但必须完整。
2. **初期规划的是文件名和边界，不是内容**：纪律是踩坑长出来的，提前建空文件会积累无人维护的样板文字，比没有更危险（看似有规矩，实际是空的）。初期定框架，每条纪律事后追加且带起因。
3. **分类粒度别过细，标准是"加载场景是否互斥"**：测试和安装通常同一次操作里发生，拆开反而要读两个文件；数据存储/编码可能一辈子没纪律条目。小项目两三个文件够，膨胀了再拆。
4. **文件头"适用场景"声明的价值是防误用，不是省 token**：它防止把 A 场景的规矩套到 B 场景。真正省 token 的是"决定读哪个文件"之前的目录判断（不相关的文件完全不进上下文）。纪律文件通常只有几十行，省的量级很小——这套体系的主要收益是**可维护性和跨会话/跨 agent 可达性**，省 token 只是副产品。
5. **软约束的诚实声明**：记忆里的"记得去读文件"是软约束。最强保证 = 记忆目录 + 技能章节双路径指向文件。想要硬保证，可以把关键检查做进脚本的收尾步骤（如 auto_test.py 退出前自动息屏），不依赖 agent 自觉。

## 五、衡量指标（体系是否运转良好）

1. 新会话中定位规矩的步数：理想 = 读记忆 → 读索引 → 读对应纪律文件，三步。
2. 记忆占用稳定在低水位，不随项目数量线性增长。
